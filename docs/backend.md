The backend has three execution boundaries: the server event loop, a graph thread, and one supervisor process per terminal. Related code stays together within those boundaries; there is no generic worker or service framework.

`core.janet` wires startup, recovery, routes, and shutdown. It also owns browser terminal subscriptions, output credit, per-pane command queues, and connection cleanup. Its `operate-terminal` function handles both HTTP and WebSocket terminal commands directly. The transport adapters handle authentication and framing; WebSocket commands do not construct HTTP requests.

The HTTP listener accepts only `127.0.0.1:<bound-port>` and `localhost:<bound-port>` authorities, including requests for the page and session token. It bounds headers at 16 KiB and request bodies at 1 MiB; error reports use 16 KiB and pane placements use 64 KiB. GET and HEAD requests cannot carry bodies. Invalid or duplicate content lengths and transfer encodings are rejected before reading the body, and rejected connections close. These limits cover HTTP requests, not responses or WebSocket traffic after upgrade. Incoming WebSocket messages retain their separate 256 KiB limit; large outgoing terminal snapshots retain the existing backpressure behavior.

`cli.janet` owns argument parsing, shell invocation, and the local document connection used by `vz`. The server calls its socket listener with the document-opening function; document behavior stays in `core.janet`. File-command quoting is handled by `file-argv`, separately from the configured Bash invocation.

`graph.janet` owns scanning, source-change detection, drawing, config diagrams, and their caches. It also owns the thread and bounded request/reply channels. `render-svg` accepts previous source stamps explicitly; animation history belongs to the running graph instance. Graphviz and scanning stay off the server event loop. The periodic watcher and explicit drawing/file requests refresh source state; unrelated requests do not walk the project.

`config.janet` owns config-line filtering and error-index remapping, along with the graph palette, named and hexadecimal colors, tints, and readable text colors. The server owns config writes. Config commands and pane metadata updates synchronously read, transform, and save the file before yielding to graph work, so server requests cannot interleave those updates. `config/read-config` returns the actual lines without creating, deduplicating, or rewriting the file. `config/initialize` explicitly creates a missing startup config. Saving normalizes commands and pane records, then atomically replaces the file so the graph thread cannot read a half-written version. Existing file permissions and symlink targets are preserved. Edits made by external programs are read on the next operation; this is not a cross-process transaction lock.

`config-graph.janet` keeps graph editing, file updates, and config diagram construction together. Reloading is observational. Append, rename, comment, and delete operate on the latest file contents and preserve pane records. The former line-editor insert/delete/reorder API is gone.

Pane metadata does not invalidate the main graph cache. Source fingerprints exclude the root config file; graph commands are compared separately. Source files, nested configs, and graph-command changes still trigger updates. Main graph drawings and config diagrams are cached independently.

The graph thread evaluates imported configs before discovery and applies local hide prefixes to both scanning and fingerprints. Effective config state is checked separately, so even an excluded nested config can unhide its files. HTML asset URLs link only to discovered files; unresolved website URLs do not become invented project-relative external nodes.

`scan.janet` owns file classification, shared parsing, discovery, and dependency resolution. It runs each language’s patterns or custom parser and supplies shared helpers when constructing a language pipeline: Python receives `blank-noise` as a function argument. Language modules never import the scanner. Parsers report imports, symbol references, assets, or explicit project-file dependencies. Named functions handle project-file linking and import resolution; a shared unique-index helper rejects ambiguous matches. Graph assembly records the resolved edges. Language-specific fallback policies remain explicit in the resolver.

Terminal supervisors own PTYs and libvterm. PTY resizing calls `ioctl(TIOCSWINSZ)` through a small fixed-argument C wrapper in `src.server/term/pty.c`, built with the application; Janet does not invoke `stty`. The wrapper retries interrupted calls and returns the captured error number. The supervisor resizes the PTY before the emulator, restores the previous PTY dimensions if emulator resizing fails, and commits reported dimensions only after both succeed. Errors propagate through the existing request logging and reply path. A failed rollback marks an emulator fault to prevent processing output with inconsistent dimensions. Output feeds the emulator once. The vterm wrapper returns raw row bytes and terminal state; the host builds versioned screen messages and Base64-encodes their rows using the shared helper in `json.janet`. WebSocket handshakes use that same helper. The emulator has no JSON or WebSocket dependency. Browser subscriptions receive screen and history snapshots or deltas, using screen revisions and session generations to recover safely. Input is acknowledged independently of output. There is no raw-output replay backlog, `since` operation, `poll` endpoint, or echo-wait path. Separate command and waiting-screen connections keep output waits from blocking input. Capturing text reads the emulator's current screen.

Run `./src/test/run` for backend coverage. The [parser corpus](parser-testing.md) checks exact multi-file dependency graphs for every language, file-order and worker-count independence, line endings, and incomplete input. Browser lifecycle, config editor, rail, resize, and stream checks exercise the public routes against isolated projects. Run suites that restart servers sequentially because they choose the first available port. Existing supervisors are preserved on server restart; they acquire supervisor code changes only when recreated.
